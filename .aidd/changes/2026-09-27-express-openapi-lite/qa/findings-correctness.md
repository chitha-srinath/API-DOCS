| 1 | HIGH | `src/spec/glob.ts:5-9` | `escapeChar` tests a single character against the **global**-flagged `REGEXP_METACHARS` regex with `.test()`, so the shared `lastIndex` state silently causes every other **consecutive** regex-metacharacter in a glob pattern to be left unescaped in the compiled `RegExp` source. | Reproduced directly (Node 24, no framework needed): `REGEXP_METACHARS = /[.+?^${}()|[\]\\]/g`; calling `escapeChar('.')` then `escapeChar('.')` again on the pattern `/a..b/x` yields the raw source `/a\..b/x` — the **first** `.` is escaped, the **second** is not, because the first successful `test()` call left `lastIndex = 1`, which makes the length-1 string for the second `.` fail the bounds check and get treated as ordinary (unescaped) text, then reset `lastIndex` back to 0 for the character after that. In `buildSpec`, an operator sets `autoDetect: { exclude: ['/a..b/**'] }` (AC-030) intending to hide the literal path `/a..b/...`; the compiled regex becomes `^/a\..b(?:/.*)?$` where the unescaped second `.` is a "match any character" metachar, so the exclude glob now **also matches** `/aXYb/anything` for any character `X` the author never intended, silently excluding unrelated plain routes from `/openapi.json` (or, symmetrically for `include`, silently admitting routes that should have been left out) with no error, log line, or test failure — `test/spec/glob.test.ts` has no case with two consecutive metacharacters, so this ships undetected. Confirmed with an inline probe reproducing exactly `src/spec/glob.ts`'s `escapeChar`/`toRegExp` logic against `/a..b/x` and `/a(.)b/x` (second case: `(` escaped, `.` left raw, `)` escaped again — the alternation is visible on any pattern with 2+ adjacent metacharacters). |
| 2 | MEDIUM | `src/introspect/paths.ts:67` | `convertExpressPath` converts named wildcards with `raw.replace(NAMED_WILDCARD, '{$1}')`, a **non-global** `.replace()`, so a path with more than one named wildcard segment only has its first `*name` converted; any subsequent `*name` is left as a literal `*name` substring in the emitted OpenAPI path template and its param name never lands in `pathParams`. | Express 5's `path-to-regexp`-based router accepts more than one named wildcard in a single pattern, e.g. `router.get('/files/*root/*rest', handler)`. Calling `convertExpressPath('/files/*root/*rest', log)` replaces only the first `*root` → `{root}`, then runs the (correctly global) `NAMED_PARAM`/`BRACED_PARAM` passes over the remaining string, which still contains the literal substring `*rest` untouched. The function returns `{ path: '/files/{root}/*rest', pathParams: ['root'] }` instead of `/files/{root}/{rest}` with `pathParams: ['root','rest']` — the generated OpenAPI document embeds a syntactically invalid/inaccurate path template (a literal `*` is not valid in an OpenAPI path item key) and drops the second path parameter's declaration entirely, silently, with no `debug`/`warn` line and no thrown error, unlike the documented skip behavior for RegExp/unnamed-wildcard routes. `test/introspect/paths.test.ts` only exercises a single wildcard per path (`/files/*rest`), so the multi-wildcard case is unverified. |
| 3 | LOW | `src/spec/build.ts:56-70` | `dedupe()`'s tie-break for equal-rank collisions (`typed` vs `describe` at the same method+path) resolves via `existing.op.id ?? ops.indexOf(existing.op)`, which silently degrades to array-position ordering (not registration-`id` ordering) whenever a `SpecOperation` is constructed without an `id` — a real path since `id` is optional on the exported `SpecOperation` type and only `specOperationsFromRegistry` (one of possibly several producers) populates it — and the array has been reordered upstream, so "earlier wins" then means "earlier in the caller's array", not "registered first", contradicting the function's own doc comment "Ties keep the earlier (lower `id`/array-index) entry" only by coincidence of wording. | A caller builds `SpecOperation[]` for two independent routers merged out of order (e.g. auto-detected/`describe()` ops from router B concatenated before ops from router A, with neither carrying `id`) and both register the *same* method+path via `describe()`; because neither has an `id`, precedence for the equal-rank collision falls back purely to whichever happened to land first in the merged array, not which `describe()` call executed first — a caller relying on "registration order wins" gets whichever operation the merge step happened to put first instead, a silent, data-dependent difference in which route's metadata appears in `/openapi.json`. |

## Areas checked and found correct

- **ADR-49 error-brand mechanism** (`src/adapter/errors.ts`, `src/config/errors.ts`, `src/core/types.ts`): the `BRAND`/`BRAND_KEY` symbol pair, `collectBrands(new.target)` walk, and the `Symbol.hasInstance` override (own-brand check with fallback to `Function.prototype[Symbol.hasInstance]` for un-branded subclasses) match ADR-49's construction and `instanceof` rules exactly in both classes, including the subclass-aware and cross-copy semantics described. Traced by hand through `new MyErr()` (subclass, no own brand) and confirmed the fallback path and the ancestor-brand match both work as specified.
- **ADR-54/ADR-56 signatures**: `createRoute(...)` (`src/route/typed.ts`) returns `route(method, localPath, meta, handler)` (4 args) and `createDescribe(...)` (`src/route/describe.ts`) returns `describe(method, localPath, meta)` (3 args), both registering synchronously via `deps.registry.register(...)` inside the factory call, exactly as ratified in ADR-54/ADR-56.
- **ADR-55 `sideEffects` fix**: `package.json`'s `sideEffects` array is the prescribed 3-element list (`./dist/auto-record.js`, `./dist/auto-record.cjs`, `src/introspect/auto-record.ts`), addressing the esbuild source-level elision root cause described in the ADR.
- **Introspection walker Express 4/5 handling** (`src/introspect/sniff.ts`, `src/introspect/index.ts`, `src/introspect/recorder.ts`): `isExpress4` never reads `app.router` on a v4 app (guards with `hasOwnProperty('_router')`/`lazyrouter`), `resolveTopmost`/`childRoot`/`getApplicationStack` branch correctly on the same test, and `findByHandle`'s dual `validatorFn`/`handlerFn` match correctly resolves typed routes even though only the first same-method stack layer (the validator) is inspected per route.
- **Spec builder determinism/canonicalization** (`src/spec/canonical.ts`, `src/spec/naming.ts`): `canonicalize` recursively sorts object keys, drops `undefined`, and never reorders arrays; `assignOperationIds` sorts by registration `id` (not array position) before suffixing collisions, giving order-independent output for the common, registry-backed path.
