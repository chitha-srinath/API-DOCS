| 1 | HIGH | `src/introspect/index.ts:69` (`ctx.registry.findByHandle(handlerFn)`) + `src/registry/registry.ts:22-25` (`entries.find(...)`) | `introspect()` calls `RouteRegistry.findByHandle`, an `O(n)` linear `Array.find` over every registered route, once per walked route layer, making the introspection pass `O(n²)` in route count instead of the `O(n)` a single-pass walk implies. | An app with `n` typed routes mounted via `apiDocs.route(...)` calls `GET /openapi.json` for the first time (cold spec-cache) or after any `apiDocs.invalidate()` / fingerprint change (e.g. a route added at runtime). Measured directly against this diff (probe deleted after the run): N=500 routes → 84.54ms; N=1000 → 98.29ms (×1.16 for 2× routes); N=2000 → 252.46ms (×2.57 for another 2× routes) — the super-linear jump from a ~1.16× to a ~2.57× multiplier as N doubles again is the quadratic signature, and N=2000 alone already breaches the ADR-26 p95<200ms budget on the rebuild path. `bench/spec-cold.bench.ts` and `test/perf/spec-endpoint.perf.test.ts` never exercise more than 2 routes, so this class of regression is invisible to the existing perf gate; any consumer with a few thousand routes (a plausible target per architecture.md's own scalability discussion of ADR-01 "scalability-first… over-builds for 1k-route scale") will see cold-start/spec-rebuild latency that scales worse than the route count itself. |
| 2 | HIGH | `src/serve/router.ts:50-52` (adapter resolution: `options.schemaAdapter ?? standardSchemaAdapter`) and `src/route/typed.ts:61-68` (`resolveAdapter`) | Neither composition-root call site wraps the resolved adapter in `memoizeAdapter` (`src/adapter/memo.ts`), so the ADR-03 WeakMap-memoized `toJSONSchema` never runs in the actual running package — every spec rebuild (cache miss / `invalidate()` / cold start) re-derives every operation's params/query/body/response JSON Schema from scratch via `adapter.toJSONSchema`, even though the same schema objects (same `meta.params`/`meta.query`/etc. identity, stored once in the registry) are reused build after build. | `memoizeAdapter` is defined and unit-tested in isolation (`test/adapter/memo.test.ts`, `test/adapter/contract.test.ts`, `test/adapter/no-jsonschema.test.ts`) but `grep -rn "memoizeAdapter" src/` shows it is exported and never imported by any other `src/**` file — it is dead code in production. Measured (probe deleted after the run): 300 routes, each with 4 zod object schemas (`params`/`query`/`body`/`response`), invalidated and re-fetched 4× in a row — without `memoizeAdapter` wired: 98.94ms, 52.99ms, 46.53ms, 42.57ms (steady-state ~42-53ms per rebuild, never drops further because nothing is cached across rebuilds); with `memoizeAdapter(standardSchemaAdapter)` passed in as `schemaAdapter` (proving the fix path exists and works): 49.25ms, 37.75ms, 25.83ms, 31.90ms — a consistent ~10-15ms (≈25-30%) reduction per rebuild that should, by design, approach near-zero for the schema-conversion portion specifically since the same schema instances recur, and would scale up with schema complexity (nested/larger zod schemas) and route count, neither of which the existing 1-route `bench/spec-cold.bench.ts` (`apiDocs.route('get', '/users/:id', {}, ...)` — an empty `meta`, so `toJSONSchema` is never even called) or the 2-route `test/perf/spec-endpoint.perf.test.ts` can surface. A consumer who reads ADR-03's own comment in `src/adapter/memo.ts:11` ("wraps any adapter with a WeakMap<schema, JSONSchema> memoization") and assumes that guarantee holds for `createApiDocs()`/`route()` out of the box is wrong: they get the unmemoized cost on every fingerprint-invalidating change, compounding with finding #1 on any app that adds routes dynamically or is restarted frequently in dev (nodemon/ts-node-dev), each restart's first request paying full, un-amortized schema-conversion cost. |
| 3 | LOW | `src/spec/cache.ts:30-34` (`fingerprint`/`countLayers`) | The spec-cache's cache-hit check itself is `O(total layer count)` per call (a full recursive walk of the router stack, including nested sub-routers) rather than `O(1)`, so every request to the spec endpoint pays a linear scan even when the cached document is returned unchanged. | Measured directly (inline Node script against a 5,000-route Express 4 app, 10,000 iterations of `fingerprint(app)`): total 217.97ms / 10,000 calls = 0.0218ms average per call — at this scale the cost is negligible relative to the 200ms ADR-26 budget and is not, by itself, a defect worth fixing under this dimension's severity bar. ## Areas reviewed with no performance finding raised

- **`src/introspect/sniff.ts`** — `isExpress4`/`sniffRoot` are `O(1)` property checks, called once per `introspect()` invocation (not per layer); no cost concern.
- **`src/introspect/index.ts` walk itself** (excluding the registry lookup in finding #1) — `walkStack`/`handleLayer`/`handleRoute` is a single depth-first pass over the router stack with per-layer `try/catch` (cheap in the non-throwing path); no additional quadratic behavior found beyond `findByHandle`.
- **`src/introspect/recorder.ts` (`installRecorder`/`annotateNewLayers`)** — wraps `use()` once at app-setup time; `wrappedUse` runs only when routes/routers are mounted, not per HTTP request, so there is no per-request dispatch overhead from the mount-recorder. `annotateNewLayers` is `O(newLayers)` (bounded by `stack.slice(before)`), not `O(total stack)`.
- **`src/adapter/memo.ts` internals** — the memoization logic itself (WeakMap/WeakSet keyed by schema identity, per-`io` slot) is correct and cheap when it *is* used (see `test/adapter/memo.test.ts`); the defect is that it is never wired in, not a flaw in the module itself (finding #2).
- **Cache invalidation correctness under concurrent load** — `createSpecCache.get()` is fully synchronous (no `await` between the fingerprint check and cache read/write), so within Node's single-threaded event loop there is no interleaving window for two concurrent requests to race on `hasValue`/`lastFingerprint`/`lastResult`; no data race found. (The documented ADR-02 "a layer replaced in place with an equal count still evades the fingerprint" gap in `src/spec/cache.ts:1-4` is a correctness/staleness risk, already called out and accepted in-repo — not re-raised here as it is not a performance defect.)
